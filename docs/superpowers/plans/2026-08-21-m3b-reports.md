# M3b Reports — Implementation Plan

**Design:** `docs/superpowers/specs/2026-08-21-m3b-reports-design.md`
**Baseline:** `7a7817f`, 242 tests passing.

## Global Constraints

**GRDB's async overload.** Inside an `async` function, `store.dbQueue.read {}`
resolves to GRDB's `async` overload and will not compile without `await`. Write
`try await store.dbQueue.read` in async contexts, `try store.dbQueue.read` in
sync ones. This has bitten every milestone so far.

**Public memberwise initialisers are internal.** A `public struct` gets an
`internal` memberwise init. Anything `KodaUITests` constructs needs an explicit
`public init`.

**`KodaCore` imports no UI framework.** `grep -rE 'import (AppKit|SwiftUI)'
Sources/KodaCore` must stay empty. `ColumnAlignment` is therefore a plain enum,
not `NSTextAlignment`.

**Never interpolate user input into SQL.** Report and filter predicates are
compile-time constants in `Reports.all`. A sort arrives as a column id and is
resolved by lookup against the report's own columns; an unknown id resolves to
nil and the sort is ignored.

**Run the fixture.** Every task that adds a query ends by running it against
`ReportFixture`, not by reasoning about whether the SQL is right.

## Task 2: Indexability

**Files:** `Sources/KodaCore/Indexability.swift` (new)

One SQL `CASE` expression, exported as a string constant, plus a matching Swift
enum for the inspector to render. Precedence per the design: redirect, client
error, server error, noindex, canonicalised, else indexable.

```swift
public enum Indexability {
    public static let expression = "CASE ... END"   // yields a short text verdict
}
```

`status = 0` is a transport error and must land in the server-error branch, not
fall through to indexable — a URL that never responded is not indexable.

**Tests** (`Tests/KodaCoreTests/IndexabilityTests.swift`): table-driven, one
fixture row per verdict, run through the actual SQL expression against a real
database so the test exercises the string that ships. Include:
- `aRedirectIsNonIndexable`
- `aClientErrorBeatsNoindex` — a 404 that also carries noindex reports the 404
- `aTransportErrorIsNonIndexable` — status 0
- `aSelfReferencingCanonicalIsStillIndexable`
- `aCanonicalPointingElsewhereIsCanonicalised`
- `anOrdinary200IsIndexable`

**Verify:** all six pass.

## Task 3: The fixture crawl

**Files:** `Tests/KodaCoreTests/ReportFixture.swift` (new)

A single helper that builds an in-memory `Store` containing one row per issue
class the eleven reports can surface. Written directly with SQL inserts rather
than by running a crawl: the crawler is not under test here and a fixture that
has to be crawled is slow and hard to extend.

It must cover, at minimum: a clean indexable page; a page with no title; two
pages sharing a title; a title over 60 and one under 30; a page with two
titles; a page whose title equals its H1; the same spread for meta description
(missing, duplicate, over 155, under 70, multiple); missing H1, duplicate H1,
multiple H1, an H1 over 70, missing H2; an image with no alt, an image with alt
over 100 chars, an image over 100KB; a missing canonical, a self-referencing
canonical, a canonicalised page, a canonical pointing at a 404; a noindex page,
a nofollow page, a page whose `x_robots_tag` contradicts its `meta_robots`; an
hreflang entry with no return link, one pointing at a 404, a set with no
x-default; a page at depth 4; a page with exactly one inlink; a 301, a 404, a
500, a transport error, a two-hop redirect chain, and a redirect loop; and an
external URL that is broken.

Expose `expected` counts as named constants so the report tests assert against
a stated intent rather than a magic number.

**Tests:** `fixtureBuildsAndHasEveryIssueClass` — asserts the fixture's own row
count and that each table is non-empty. This test exists so a broken fixture
fails once, here, rather than as eleven confusing report failures.

## Task 5: Query building in the store

**Files:** `Sources/KodaCore/Store+Reports.swift` (new)

```swift
public struct ReportRow: Sendable, Identifiable {
    public let id: Int64
    public let cells: [String?]     // column order; nil is a genuine NULL
}

extension Store {
    public func ids(for report: Report, filter: ReportFilter,
                    sortBy: ReportColumn?, ascending: Bool) throws -> [Int64]
    public func rows(ids: [Int64], columns: [ReportColumn]) throws -> [ReportRow]
}
```

`ids` builds `SELECT u.id \(ReportSQL.from) WHERE (report) AND (filter) ORDER BY
(expr IS NULL) ASC, expr DIR, u.id ASC`, preserving M3a's nulls-last-in-both-
directions rule. A nil `sortBy` means discovery order (`u.id`).

`rows` fetches by primary key only — `WHERE u.id IN (...)` with no predicate —
so it stays O(1) per row however deep the slice is. It reorders the result to
match `ids`, as `RowStore` does today, because `IN` does not preserve order.

Cell formatting lives here, in one place: `NULL` becomes nil, integers and reals
become their digits, blobs become a short hex prefix, text passes through.

**Tests** (`Tests/KodaCoreTests/StoreReportsTests.swift`):
- `idsRespectTheReportAndFilterPredicates`
- `idsSortAscendingAndDescending`
- `idsPutNullsLastInBothDirections`
- `idsWithNoSortAreInDiscoveryOrder`
- `rowsComeBackInTheOrderOfTheIdsGiven` — shuffle the ids and assert
- `rowsRenderNullAsNilNotEmptyString` — the table needs to tell them apart
- `rowsForAnEmptyIdListIsEmptyAndRunsNoQuery`

**Verify:** all pass; `rowsComeBackInTheOrderOfTheIdsGiven` must fail if the
reorder step is removed. Prove that by removing it once.

## Task 6: Counts in one pass

**Files:** `Sources/KodaCore/Store+Counts.swift` (new)

```swift
extension Store {
    /// Keyed "reportID.filterID".
    public func counts(for reports: [Report]) throws -> [String: Int]
}
```

Builds one `SELECT sum(CASE WHEN (report) AND (filter) THEN 1 ELSE 0 END) AS
c0, ... \(ReportSQL.from)`. Aliases are positional (`c0`, `c1`) rather than
derived from ids, because a report id containing a character SQLite dislikes
would otherwise break the query; the mapping back to keys is held in Swift.

SQLite's limit on expressions in a SELECT is well above 50, but assert the
count is under 500 and split into chunks above that, so this cannot become a
latent cap.

**Tests** (`Tests/KodaCoreTests/StoreCountsTests.swift`):
- `oneScanAgreesWithRunningEveryFilterSeparately` — the important one. For every
  report and filter, compare `counts` against `ids(...).count`.
- `countsAreZeroNotMissingForAFilterThatMatchesNothing`
- `countsOnAnEmptyDatabaseAreAllZero`

**Verify:** the agreement test passes across all ~50 filters.

## Task 7: `RowIndex` and `RowStore` on reports

**Files:** `Sources/KodaUI/RowIndex.swift`, `Sources/KodaUI/RowStore.swift`

`RowIndex` stops holding its own SQL and delegates to `Store.ids(for:...)`. It
gains `report`, `filter`, and `sortColumnID`, replacing the `SortColumn` enum.
`SortColumn` and `URLTableColumn` are deleted; their tests move to the new
shape.

`appendNewIds()` is kept but now only applies when the sort is discovery order
**and** the report is Internal with its All filter. Any other report can have a
new row that belongs anywhere in the order, or that the predicate excludes —
appending would corrupt the view. This is the same reasoning that limited
appending to the default sort in M3a, extended to reports.

`RowStore` swaps `CrawlRow` for `ReportRow` and delegates to `Store.rows(ids:
columns:)`. Its LRU, page size, and reorder behaviour are unchanged.

**Tests:** extend `RowIndexTests` and `RowStoreTests`:
- `rebuildUnderANonDefaultReportUsesThatReportsPredicate`
- `appendIsRefusedOutsideInternalAll`
- `switchingFilterChangesTheRowSet`
- existing tests updated, not deleted — the M3a guarantees still hold

**Verify:** `swift test --filter RowIndex` and `--filter RowStore` green.

## Task 8: The table on dynamic columns

**Files:** `Sources/KodaUI/URLTableView.swift`

`URLTableCoordinator` takes the selected `Report` and reads cells positionally
from `ReportRow.cells`. `NSTableColumn` identifiers become column ids.

Because the column set changes when the tab changes, `updateNSView` must rebuild
the table's columns when the report id changes, not only reload data. Rebuilding
on every update would drop the user's scroll position twice a second, so it is
guarded on the report actually having changed.

Selection must survive a reload, as it does today, but must be *cleared* when
the report changes — row 4 of Titles is not row 4 of Images, and keeping the
index would silently select an unrelated URL.

**Tests** (`URLTableCoordinatorTests`, extended):
- `cellsComeFromTheReportsColumnOrder`
- `aNullCellRendersEmpty`
- `sortDescriptorResolvesToAColumnOfTheCurrentReport`
- `aSortDescriptorForAnotherReportsColumnResolvesToNil`

**Verify:** green, and `swift build` still warning-free.
